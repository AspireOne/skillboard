# Skillboard

A small desktop-style app for `~/.agents`. You can browse and edit skills and `AGENTS.md`, lint skills, see how much always-on context the skill descriptions cost and how often each skill is used, park skills in `skills-purgatory/`, and check that each harness links back to `~/.agents`.

Launched inside a project, it also shows the project's own `AGENTS.md` and `.agents/skills`, at every level up to the repository root.

```sh
go build -o ~/.local/bin/skillboard ./cmd/skillboard   # install; `skills` is an alias in ~/.zshrc
skillboard                                             # opens the app window, returns the terminal
skillboard -project ~/dev/some/repo                     # look for projects there instead of the working directory
skillboard -foreground -open=false -addr 127.0.0.1:7979   # development: serve here, logs to the terminal
```

## Design notes

- **No lingering server.** The launcher opens a free port, re-runs itself detached (`setsid`, the listener passed as fd 3), opens a Chromium `--app` window and returns. The window uses its own browser profile (`%LOCALAPPDATA%\Skillboard\Browser` on Windows, `~/.cache/Skillboard/Browser` on Linux). Without it, the launch is handed to the browser that is already running, which ignores window flags like `--start-maximized`. The window holds `/api/live` open. The process exits 4 seconds after the last window disconnects, or after 60 seconds if no window ever connects. The detached process logs to `~/.local/state/skillboard.log`, which is overwritten on each launch.
- **One window.** A launch that opens a window first asks the instance recorded in `~/.local/state/skillboard-instance.json` what it shows. If it shows the same scopes from the same build (the binary's mtime), the launch only focuses its window. Otherwise the launch starts its own server and tells the old window over `/api/live` to save and move to the new URL. The old server then exits like any other whose window left. This avoids closing and reopening windows, which browsers make unreliable. Focusing works under WSL only, through PowerShell; elsewhere a second window opens. Launches with `-open=false` skip all of this, so development servers never touch the real window.
- **Single binary.** The frontend is plain ES modules in `web/static/`, embedded with `go:embed`. CodeMirror is one pre-built bundle in `web/static/vendor/`. Rebuild it with `scripts/vendor-codemirror.sh` only when bumping versions. The app needs no Node.
- **Live preview editor** (`web/static/editor.js`). Markdown renders in place, and a line shows its raw syntax only while the cursor is on it. The Markdown parser reads frontmatter as a rule plus a setext heading, so the editor finds the frontmatter range itself and skips it.
- **The disk is the source of truth.** Agents edit these files too. The UI autosaves and polls `/api/tree`. An unedited file reloads silently, through a minimal diff that keeps the cursor in place. Saves send the mtime the editor loaded, and the server refuses a stale write with 409.
- **Mtimes are Unix microseconds.** Nanoseconds exceed JavaScript's exact integer range, so a round-tripped value would never match and every save would conflict.
- **Files are saved verbatim.** Nothing rewrites frontmatter or reformats YAML, except a lint fix you click. A fix edits only the lines it needs, so comments and layout survive. The server lints again before it applies a fix, and refuses one whose issue has changed, that leaves the issue in place, or that causes a new error. Lint values come from the server.
- **Rendered Markdown can contain raw HTML,** so the server sends a CSP that blocks inline scripts. This origin can write files.
- **Project scopes.** Every directory with an `AGENTS.md` or `.agents/` from the working directory up to the repository root (`.git`) is its own scope, nearest first. Harnesses load all of them, so a monorepo package shows its own files and the repository's. The walk never reaches `~` or `~/.agents`, whose `AGENTS.md` is the global one. Every path the API hands out starts with its workspace ID (`project-1/…`, `global/…`), so paths stay unique, and the server refuses paths outside the instruction files and skills directories. That matters because a project's root is part of a repository.
- **Machine-local skills.** Skills that your dotfiles repository ignores are marked `local`, since they don't sync to your other machines. Git decides (`git check-ignore`), so `.gitignore` stays the only list. The repository is the bare one at `~/.cfg`, with `~` as its work tree; set another with `-dotfiles`. Without it, nothing is marked.
- **Shadowed skills.** Claude Code prefers a personal (global) skill over a project skill with the same name, so such a project skill gets a lint warning.
- **Harness links** (`internal/harness`) cover only harnesses that do not read `~/.agents` natively. Codex reads `~/.agents/skills` itself, so a `~/.codex/skills` directory would only shadow it. In a project, only Claude Code needs a link (`.claude/skills → ../.agents/skills`). Creating or restoring a skill creates a missing link to its skills directory, and the overview offers to create any other missing link. Nothing that already exists is ever replaced.
- **Skill usage** (`internal/usage`) comes from the local transcripts of Claude Code (`~/.claude/projects`), Codex (`~/.codex/sessions`, `archived_sessions`) and Pi (`~/.pi/agent/sessions`). A use is the model calling Claude's `Skill` tool or reading a `skills/<name>/SKILL.md` in a Codex or Pi tool call, or the user typing `/name`, `$name` or `/skill:name`. Each skill counts once per session. Skill lists in prompts name every skill, so they are never counted. Usage is matched to skills by name. The results are cached per transcript in `~/.cache/Skillboard/usage.json`, and the cache keeps the usage of deleted transcripts, because Claude Code deletes its own after 30 days. Codex's analytics endpoint reports far fewer uses than its transcripts show, so it is not used. Transcripts are read once per launch.
